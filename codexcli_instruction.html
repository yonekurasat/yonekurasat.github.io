1. Codex CLIの全体像

Codex CLIは、ローカルのターミナルから使うコーディングエージェントです。コードを読み、編集し、コマンドを実行し、差分やテスト結果を見ながら作業できます。

💬

対話する

TUI上で依頼、追加指示、スラッシュコマンド、ファイル指定を行います。

🛠️

編集・実行する

ワークスペース内でコード編集やテスト実行を行い、必要に応じて承認を求めます。

🔍

レビューする

/diff や /review で差分、リスク、テスト不足を確認できます。

1
起動codex でリポジトリ内から開始
2
計画/plan で影響範囲と手順を確認
3
編集スコープを絞って実装
4
検証! npm test などで確認
5
レビュー/diff と /review
⌨️

3. スラッシュコマンドの使い分け

/plan、/diff、/review、/statusを中心に、作業の粒度に応じて使い分けます。

計画・進行管理

コマンド使いどころ
/plan実装前に影響範囲、手順、リスクを出す
/goal長い作業の達成目標を固定する
/compact長くなった会話を要約してコンテキスト節約
/side / /btw本線から外れた確認をする
/fork今の会話から別案を試す

差分・レビュー

コマンド使いどころ
/mention特定ファイルやフォルダを会話に添付
/diffGit差分、未ステージ、未追跡ファイルを確認
/review現在の作業ツリーをレビューさせる
/copy直近の完了済み出力をコピー
/statusモデル、権限、書き込み範囲、トークン状況を確認

安全・権限

コマンド使いどころ
/permissionsCodexが自動実行できる範囲を調整
/approve拒否された操作を1回だけ承認して再試行
/debug-config設定の読み込み順やポリシー制約を調査
/raw長い出力をコピーしやすい表示にする
/ps / /stopバックグラウンド端末の確認・停止

設定・拡張

コマンド使いどころ
/initAGENTS.md のひな形を作る
/mcpMCPサーバー・ツールを確認
/appsconnector / app をプロンプトに挿入
/skillsローカルskillを選ぶ
/keymap / /vimキー操作やVimモードを変更
💡
/plan は大きい変更の入口。

いきなり「実装して」ではなく、まず計画、影響範囲、テスト観点、リスクを出させると失敗が減ります。

💻

4. ! でシェルコマンドを打つ

TUI内で ! からコマンドを投げると、確認結果をそのまま次の会話に使えます。

よく使うコマンド

! git status
! git diff
! npm test
! pnpm lint
! pytest
! cargo test
! rg "TODO|FIXME" .

使い方のコツ

短い確認は自分で実行git status、test、lintなどは ! で素早く。
失敗ログをCodexに渡す「この失敗を直して」と続けるだけで文脈に載る。
実行中なら Tab でキュー今のターン終了後に ! npm test を走らせられる。
🚀

5. 起動時オプション

普段は安全寄りの設定で起動し、必要なときだけモデルやサンドボックスを切り替えます。

codex --cd path/to/repo
codex --model gpt-5.5
codex --sandbox workspace-write --ask-for-approval on-request
codex --image screenshot.png "この画面に合わせて修正して"
codex --search "最新のAPI仕様に合わせて実装を確認して"
codex -c model_reasoning_effort=high

作業場所

--cd / -C で作業ディレクトリを指定。--add-dir で追加ディレクトリを許可。

モデル

--model や -c model_reasoning_effort=high でモデル・推論強度を調整。

危険モード

--yolo は承認とサンドボックスを回避。隔離環境以外では非推奨。

🛡️

6. サンドボックスと承認

Codexの安全性は「どこまで実行できるか」と「いつ人間の承認を求めるか」で決まります。

おすすめの考え方

場面推奨
コードを読ませるだけread-only
普段の実装・修正workspace-write + on-request
CIや隔離コンテナnever や --yolo を慎重に検討
秘密情報が多いrepopermission profileでdenyルールを設定
codex --sandbox workspace-write --ask-for-approval on-request

7. AGENTS.mdは早めに作る

毎回同じ説明をする代わりに、プロジェクトのルール、テスト方法、禁止事項、完了条件を書いておきます。

生成

/init

ひな形を作ったら、チームの実態に合わせて短く正確に直すのがコツです。

テンプレート例

# AGENTS.md

## Project layout
- src/: application code
- tests/: test code
- docs/: design notes

## Commands
- Install: pnpm install
- Lint: pnpm lint
- Test: pnpm test
- Typecheck: pnpm typecheck

## Rules
- Do not add production dependencies without asking.
- Keep public API compatibility unless explicitly requested.
- After changing behavior, update tests.

## Done when
- Lint passes.
- Relevant tests pass.
- /diff shows only intentional changes.
⚙️

9. codex execは自動化・CI向け

対話せずに最後まで走らせたいときは codex exec または codex e を使います。

基本例

codex exec "テスト失敗原因を調べて、修正案を出して"
codex e --json "lintエラーを直して"
codex e - < prompt.md
codex e --output-last-message result.md "変更点を要約して"

便利なオプション

オプション用途
--jsonJSONLイベントとして出力
-o最終応答をファイル保存
--output-schema最終応答をJSON Schemaで検証
--ephemeralセッション履歴をディスクに残さない
resume --last前回セッションを再開

10. 実務ワークフロー

「小さい修正」「大きい改修」「デバッグ」「レビュー専用」で使い方を分けると安定します。

🔧

小さい修正

/mention src/foo.ts
境界条件バグを直して。既存APIは変えないで。

/diff
! npm test -- foo
/review
🏗️

大きい改修

/plan 認証処理を refresh token ベースに移行したい。
影響範囲、移行手順、必要なテスト、リスクを先に出して。
🐛

デバッグ

! npm test
この失敗ログを見て、原因を特定して。
修正前に仮説を3つ出して。
👀

レビュー専用

/review
/diff

codex exec --sandbox read-only "この差分をレビューして"
✍️

11. 良い依頼の型

最初のプロンプトに Goal / Context / Constraints / Done when を入れると、作業品質が安定します。

良い例

Goal: APIレスポンスの型変更に追従する。
Context: src/api/client.ts, src/components/UserCard.tsx, tests/user-card.test.ts
Constraints: public component APIは変えない。新規依存は追加しない。
Done when: pnpm test と pnpm typecheck が通る。

悪い例

なんか直して

曖昧すぎると、不要な編集、テスト漏れ、スコープ逸脱が起きやすくなります。

🧾

12. 最低限覚える「鉄板セット」

このセットだけでも、普段の開発でかなり使えます。

/plan /mention /diff /review /status /compact /init Ctrl+T Ctrl+R ! <command> Tab 
codex --sandbox workspace-write --ask-for-approval on-request
✅
長く使うリポジトリでは最初に /init。

AGENTS.mdにテストコマンド、設計ルール、禁止事項、完了条件を書いておくと、Codex CLIの精度が上がります。
